# Communication client et parties prenantes

## Objectif du document
Décrire la communication projet avec le commanditaire/porteur, les utilisateurs métier et les parties prenantes actuelles ou futures.

## Contexte
Le projet ne repose pas sur un client officiel unique à ce stade. La validation est principalement portée par le porteur du projet, avec échanges métiers ponctuels et perspective de clubs témoins.

## Parties prenantes concernées
- Commanditaire / porteur du projet
- Utilisateurs métier (coachs, analystes)
- Clubs témoins futurs
- Utilisateurs cibles (assistants coachs, étudiants STAPS, formateurs, clubs amateurs)

## Modalités de communication
- Démonstrations fonctionnelles ciblées.
- Retours contextualisés sur parcours métier.
- Revue des arbitrages et priorités.
- Partage d’état d’avancement via documentation.

## Supports utilisés
- Démonstrations
- Captures
- Documentation projet
- Page de statut
- Tutoriel landing page
- Comptes rendus
- GitHub Issues (suivi technique)

## Comptes rendus
Les synthèses d’échanges et décisions doivent être tracées dans les documents de pilotage et/ou templates dédiés.

## Communication en cas d’incident
- Information technique via GitHub Issues.
- Information disponibilité via page de statut Uptime Kuma.
- Canal incident détaillé : À compléter.

## Limites actuelles
- Validation métier externe encore limitée.
- Fréquence de communication non encore formalisée avec clubs témoins.

## Améliorations prévues
- Formaliser un calendrier de points avec utilisateurs métier.
- Structurer un format standard de compte-rendu décisionnel.
- Intégrer davantage de retours terrain dans la priorisation.
